# MarketHub — Laravel

Окружение для [тестового задания](task/README.md): Laravel 13, PHP 8.3,
PostgreSQL 17, очередь в PostgreSQL и Mailpit.
Реализованы приём и сохранение вебхуков, фоновая проверка и обновление заказов,
позиций и истории статусов с защитой от повторов и устаревших снимков.
Письма покупателям отправляются через очередь в Mailpit. API отдаёт список заказов
и карточку заказа для админки.

## Запуск с нуля

Нужен только запущенный Docker с Docker Compose. PHP, Composer и Node.js на хосте не нужны.

```sh
sh scripts/setup.sh
```

Скрипт создаёт `.env`, собирает PHP-образ, устанавливает зависимости по lock-файлам,
генерирует ключ приложения и секрет вебхуков, применяет миграции
и запускает приложение, PostgreSQL, воркер очереди и Mailpit.
Повторный запуск сохраняет существующие ключи и данные.

## Адреса

| Сервис | Адрес |
| --- | --- |
| Приложение | http://localhost:8000 |
| Проверка HTTP | http://localhost:8000/up |
| API заказов | http://localhost:8000/api/orders |
| Mailpit — просмотр писем | http://localhost:8025 |
| SMTP с хоста | localhost:1025 |
| PostgreSQL с хоста | localhost:5433 |

База, пользователь и пароль для локальной разработки: `markethub`, `markethub`,
`local-password`. Внутри Docker приложение обращается к `db:5432` и `mailpit:1025`.
Порты можно изменить в `.env` (`APP_PORT`, `DB_FORWARD_PORT`, `MAILPIT_PORT`,
`MAILPIT_SMTP_PORT`); при смене порта приложения обновите `APP_URL`.
Секрет подписи задаётся в `.env` через `MARKETPLACE_WEBHOOK_SECRET`.

## Работа с проектом

Для коротких команд доступен `Makefile` (нужен `make` на хосте):

```sh
make help                          # Все доступные команды
make setup                         # Подготовка с нуля
make up                            # Запуск окружения
make test                          # Все тесты
make test-webhook                  # Только тесты вебхуков
make test FILTER=test_checks_timestamp_window_in_both_directions
make test ARGS="--compact"          # Дополнительные аргументы
make artisan ARGS="route:list"      # Команда Artisan
make composer ARGS="install"        # Команда Composer
make migrate                       # Применение миграций
make logs SERVICES=app              # Логи приложения
make queue-restart                 # Перезапуск воркера
make pint                          # Исправление форматирования через Laravel Pint
make pint ARGS="--test"            # Проверка без изменения файлов
make lint                          # Проверка форматирования
make format                        # Исправление форматирования
make down                          # Остановка и удаление контейнеров
```

`POST /api/webhooks/marketplace` проверяет подпись, заголовки, JSON и общие поля
события (`id`, `type`, `created_at`, `data.order`), сохраняет событие и задание очереди,
затем возвращает `200 OK`.
Таблица `webhook_events` содержит ID события MarketHub (`event_id`), тип,
исходное тело запроса (`raw_body`), время получения (`received_at`), статус `pending`
и время постановки в очередь (`queued_at`).
ID события защищён уникальным ограничением базы. Вставка использует
`ON CONFLICT (event_id) DO NOTHING RETURNING id`: только новая запись ставится в очередь.
Повторная доставка возвращает `200 OK` без чтения существующего события и вызова постановки
в очередь. Исходное тело и время получения не меняются. Другие ошибки базы не игнорируются.
Событие, задание и отметка `queued_at` сохраняются в одной транзакции:
очередь `database` должна использовать то же соединение с базой, что и приложение
(по умолчанию так и настроено).
Техническая ошибка при сохранении события или задания откатывает транзакцию и приводит к ответу 500; MarketHub повторит доставку.
Неизвестные типы событий тоже сохраняются и ставятся в очередь.

Задание `ProcessMarketplaceWebhook` получает внутренний ID записи, загружает сохранённое
тело и проверяет снимок заказа у известных типов событий. Результат фиксируется в записи:

| Статус | Значение |
| --- | --- |
| `pending` | Ожидает обработки или повторной попытки |
| `processed` | Снимок применён к заказу, позиции и история сохранены |
| `ignored` | Снимок не заменил актуальный заказ; событие учтено в истории |
| `invalid` | Ошибки полей заказа сохранены в `validation_errors` |
| `unsupported` | Тип события неизвестен; исходные данные сохранены |
| `failed` | Техническая ошибка после исчерпания попыток; причина в `last_error` |

`checked_at` содержит время завершения проверки, а `queued_at` — время постановки в очередь.
Повторное выполнение завершённого события не меняет результат.
Ошибки данных не вызывают повторов задания; технические исключения передаются воркеру
(в Docker настроены 3 попытки). Упавшее задание можно повторить стандартной командой
`php artisan queue:retry <uuid>` через `make artisan ARGS="queue:retry <uuid>"`.

Исходное тело события сохраняется без изменений при любом результате.

Обработчик заполняет таблицы `orders`, `order_items`, `order_status_history`.
Заказ содержит актуальный снимок, позиции связаны с ним через `order_id`,
а история дополнительно ссылается на исходное событие через `webhook_event_id`.
Суммы хранятся как `decimal(18, 2)` и читаются строками; даты маркетплейса отделены
от технических `created_at` и `updated_at`.

Актуальность определяется по `data.order.updated_at`. При одинаковом времени приоритет:
`created < paid < shipped < delivered < cancelled`. Если совпадают и время, и статус,
остаётся первый применённый снимок. Более свежий снимок может исправить статус назад.
Поздние события дополняют историю. Сохранение заказа, позиций, истории и результата
события выполняется в одной транзакции с блокировкой заказа.
Допущения и ограничения описаны в [DECISIONS.md](DECISIONS.md).

## Письма покупателю

После применения снимка со статусом `paid`, `shipped` или `cancelled` создаётся
уведомление и отдельное задание `SendOrderNotification`. Запись уведомления и задание
фиксируются в той же транзакции, что и заказ. Письма содержат состав и сумму оплаты,
данные отслеживания доставки либо причину отмены и информацию о возврате в течение
10 дней, если оплата известна. `created` и `delivered` писем не создают.

Письма можно посмотреть на http://localhost:8025. Перед отправкой задание заново
проверяет статус заказа и берёт актуальные данные покупателя и заказа.
Проверка и подготовка выполняются в короткой транзакции; SMTP вызывается после её
завершения, без блокировок. Статус может измениться между проверкой и отправкой.
Устаревшее уведомление пропускается. Для каждого заказа допускается одно письмо
каждого вида, независимо от числа событий и повторных выполнений задания.

Таблица `order_notifications` хранит журнал: `pending`, `sending`, `sent`, `skipped`
и `uncertain`, время попытки и отправки, причину ошибки. При неопределённом результате
SMTP повторная отправка блокируется: нужно проверить Mailpit. Ошибка SMTP отражается
также в `failed_jobs`. После аварийного завершения воркера запись может остаться
в `sending`; повтор задания её не отправляет. Подробности компромисса — в `DECISIONS.md`.

## API заказов

`GET /api/orders` возвращает список заказов в стандартном формате пагинации
Laravel (`data`, `links`, `meta`). Доступны фильтры `status` и `email`;
email сравнивается без учёта регистра. Список отсортирован по времени оформления:
сначала новые заказы. Параметры `page` и `per_page` управляют пагинацией
(по умолчанию 1 и 20; `per_page` — не больше 100).

`GET /api/orders/{id}` возвращает заказ по идентификатору MarketHub вместе
с позициями и историей статусов. Если заказа нет, возвращается `404`.
Action `GetOrderDetails` загружает заказ и обе связи в короткой транзакции PostgreSQL
`REPEATABLE READ`: карточка отражает один согласованный снимок,
даже если воркер обновляет заказ между запросами. Чтение не блокирует обновление заказа.
Формат ответов описан в [OpenAPI-контракте](task/openapi.yaml).

```sh
curl 'http://localhost:8000/api/orders?status=paid&per_page=10'
curl 'http://localhost:8000/api/orders/ord_7Q2KX9M4'
```

```sh
# Запуск после остановки
docker compose up -d --wait

# Artisan и Composer
docker compose exec app php artisan migrate
docker compose exec app composer install

# Тесты и форматирование
docker compose exec app php artisan test
docker compose exec app vendor/bin/pint --test

# Логи и состояние
docker compose ps
docker compose logs -f app queue

# Перезапуск воркера после изменения кода заданий
docker compose restart queue

# Остановка с сохранением данных PostgreSQL
docker compose down
```

Приложение использует локальный сервер `artisan serve`; окружение предназначено для разработки.
Тесты по умолчанию используют SQLite в памяти и не меняют рабочую PostgreSQL.
Группа `postgresql` с проверками карточки заказа при этом пропускается:
она проверяет PostgreSQL-специфичную изоляцию транзакций и конкурентное обновление
через два независимых соединения.

Для полного набора тестов создайте отдельную базу (один раз):

```sh
docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" markethub_test'
```

Затем запускайте тесты на ней; таблицы этой тестовой базы будут пересоздаваться:

```sh
docker compose exec -T -e DB_CONNECTION=pgsql -e DB_DATABASE=markethub_test app php artisan test
# Только карточка заказа, включая конкурентное чтение
docker compose exec -T -e DB_CONNECTION=pgsql -e DB_DATABASE=markethub_test app php artisan test --group=postgresql
```

Исходные материалы задания в `task/` сохранены без изменений.
