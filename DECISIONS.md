# Принятые решения

## Обработка событий и заказов

После проверки подписи и общих полей сохраняем исходный вебхук и задание очереди
в одной транзакции PostgreSQL. Возвращаем `200` после сохранения; техническая ошибка
даёт `500` для повторной доставки. Уникальный `event_id` исключает повторную обработку.
Поля заказа проверяет воркер: ошибочные и неизвестные события остаются для разбора.
Изменения заказа, позиций, истории и постановка письма в очередь фиксируются вместе.
Блокировки защищают от одновременного изменения одного заказа.

Актуальность определяем по `data.order.updated_at`. Более старый снимок не заменяет
заказ. При равном времени используем приоритет
`created < paid < shipped < delivered < cancelled`; при равном статусе остаётся
первый снимок. Историю пересобираем по проверенным событиям, включая устаревшие,
чтобы учитывать позднюю доставку. Отсутствующие переходы не придумываем.

Суммы храним в `decimal(18, 2)` и отдаём строками. API реализовано по OpenAPI-контракту
через Laravel Resources.
Карточку читает отдельный Action `GetOrderDetails`: заказ, позиции и история загружаются
в одной транзакции PostgreSQL `REPEATABLE READ`. Это сохраняет согласованность
ответа при параллельном обновлении заказа без блокировки воркера.

Для необязательной админки выбран Filament: задача требует стандартного списка
заказов с фильтрами и карточки со связанными данными. Готовые компоненты Filament
работают с существующими моделями Eloquent и позволяют быстро добавить интерфейс
без отдельного фронтенда, сосредоточившись на обработке вебхуков. Создание,
редактирование и удаление заказов отключены: для задачи нужен только просмотр.
Авторизацию не добавляли по условиям задания.

## Письма и ограничения

На заказ отправляем одно письмо каждого вида: оплата, доставка, отмена.
Перед отправкой проверяем текущий статус; устаревшие уведомления пропускаем.
Пропущенное уведомление можно запланировать снова, если статус восстановлен.

SMTP вызывается вне транзакции, чтобы сетевой запрос не удерживал блокировку заказа.
Статус может измениться между проверкой и отправкой — это ограничение решения.
До SMTP фиксируем `sending`; при неопределённом результате повторно не отправляем:
сервер мог уже принять письмо. Это предотвращает автоматические дубли, но допускает
пропуск письма при аварии и требует ручной проверки Mailpit.

## Вопросы и допущения

- Есть ли версия заказа? Пока одинаковое время разрешаем приоритетом статусов
  и первым применённым снимком; достоверно выбрать последний без версии нельзя.
- Необратима ли отмена? Пока более свежий снимок может исправить любой статус.
- Что означает очистка дат оплаты и отмены? Заказ отражает новый снимок,
  ранее сообщённые факты остаются в истории.
- Нужно ли досылать письма о пропущенных этапах? Пока уведомляем только
  об актуальном статусе: первый `shipped` не вызывает письмо об оплате.
  Возврат при отмене упоминаем при заполненном `paid_at` текущего снимка.

## Дальнейшие улучшения

Настроить уведомления администраторов о событиях с неизвестным типом,
чтобы своевременно обнаруживать расширения контракта MarketHub и добавлять их обработку.
Добавить мониторинг и разбор зависших событий и уведомлений. Для отправки выбрать
провайдера с идемпотентными запросами и проверкой статуса сообщения:
повтор с тем же ключом не создаст второе письмо; принятие ещё не гарантирует доставку.
При росте числа событий заменить полную пересборку истории на инкрементальную.
Построение истории статусов можно вынести в отдельное асинхронное задание.
Для этого нужно дополнительно обеспечить согласованность заказа и истории
при параллельной обработке и повторах заданий, а также учесть временное отставание
истории от актуального состояния заказа в API.
